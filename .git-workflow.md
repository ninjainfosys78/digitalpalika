# Ninja Infosys Git Workflow

This document defines the branching strategy, commit conventions, pull request standards, and release policies for all repositories at Ninja Infosys.
It applies to the `landing-page` project and all subsequent web or infrastructure projects.

---

## 1. Branching Model

All repositories must follow a strict hierarchical branch model.
Branches are always derived from the closest stable integration point.

| Branch      | Description                                           | Source      | Merge Target      | Deletion Policy           |
| ----------- | ----------------------------------------------------- | ----------- | ----------------- | ------------------------- |
| `main`      | Production-ready code. Represents the deployed state. | `release/*` | none              | Never deleted             |
| `develop`   | Integration branch for next release.                  | `main`      | `release/*`       | Never deleted             |
| `feature/*` | Feature or user story implementation.                 | `develop`   | `develop`         | Deleted after merge       |
| `hotfix/*`  | Urgent fix for production issues.                     | `main`      | `main`, `develop` | Deleted after merge       |
| `release/*` | Pre-release stabilization branch.                     | `develop`   | `main`            | Deleted after release tag |

Branch names must be lowercase, hyphen-separated, and include context.

**Examples:**
feature/us-2-header
feature/us-3-hero-section
hotfix/fix-font-loading
release/v1.0.0

---

## 2. Commit Convention

Commits must be atomic, descriptive, and tied to a Tuleap Artifact ID for full traceability.

### Commit Message Format

[#<ArtifactID>] <type>: <concise summary>

<optional detailed explanation>

Refs: <related artifact IDs or links>

### Types

| Type     | Purpose                                    |
| -------- | ------------------------------------------ |
| feat     | New feature or user story implementation   |
| fix      | Bug fix                                    |
| chore    | Non-functional changes (tooling, config)   |
| docs     | Documentation-only changes                 |
| refactor | Code restructuring without behavior change |
| style    | Formatting, indentation, or linter fixes   |
| test     | Adding or updating test cases              |
| ci       | Changes to build or deployment pipelines   |

**Example:**
[#2] feat: implement responsive header layout and CTA

Added responsive breakpoints, integrated CDN logos, and implemented language selector.
Refs: #1, #8

---

## 3. Pull Request (PR) Process

1. Create PR from `feature/*` → `develop`
2. Ensure all commits reference valid Tuleap IDs.
3. Each PR must include:

   - Title: `[Feature/Hotfix] short summary`
   - Linked Tuleap user story ID
   - Checklist of acceptance criteria
   - Screenshots or test logs when applicable

4. At least one peer reviewer must approve.
5. All CI checks (lint, test, build) must pass before merge.
6. Merge method: **Squash and merge.**
7. After merge, delete the source branch.

---

## 4. Release Process

1. Create branch `release/vX.Y.Z` from `develop`.
2. Run complete regression + QA.
3. Fix bugs in this branch only.
4. Tag release after validation:
   git tag -a vX.Y.Z -m "Release X.Y.Z – Landing Page"
   git push origin vX.Y.Z
5. Merge release → `main` and back-merge → `develop`.
6. Deploy production from `main`.

---

## 5. Hotfix Procedure

- Branch `hotfix/<issue>` from `main`.
- Commit with `[hotfix]` prefix and Tuleap bug ID.
- Test, then merge to both `main` and `develop`.
- Tag with patch version increment (`v1.0.1`).

---

## 6. Code Ownership and Reviews

- Every feature must have a responsible engineer.
- Reviews enforce:

  - No direct commits to `main` or `develop`.
  - Commit hygiene and documentation completeness.
  - Security and accessibility checks for frontend changes.

---

## 7. Continuous Integration

Forgejo Actions or external runner executes:

1. `npm ci`
2. `npm run lint`
3. `npm run test`
4. `npm run build`
5. Deploy to staging on merge into `develop`.

---

## 8. Commit Hooks

Developers must install `.gitmessage` template (see below) and pre-commit lint hook:
git config commit.template .gitmessage

---

## 9. Tagging Rules

Semantic versioning:
MAJOR.MINOR.PATCH

Examples:

- `v1.0.0` → Initial landing page release
- `v1.1.0` → Adds new Insights section
- `v1.1.1` → Bug fixes or optimizations

---

## 10. Traceability Rules

Every code change must map to a Tuleap artifact:

- Use `[#ID]` in commit message.
- Use same ID in branch name.
- Never merge untracked commits.

---

## 11. Governance

Violations of this workflow (missing IDs, unreviewed merges, direct pushes) are blocked by CI policy or reverted manually.
This workflow is owned by the **Ninja Infosys Engineering Governance Board**.
